## What Changed Between v0.3.x and v0.4.x

PR #364 (JANG support) was merged into v0.3.x but JANG was **removed** from v0.4.x:
- No `omlx/engine/jang.py`
- No JANG detection in `model_discovery.py`
- No JANG routing in `engine_pool.py`
- Scheduler rewritten for mlx-lm 0.31.3 (no `Batch` class)

## What We Need To Add

### 1. `omlx/engine/jang.py` — JANG engine (new file)
Port from our v0.3.x work with these simplifications:
- **Remove** MODEL_REMAPPING save/restore (native gemma4 in mlx-vlm 0.6.3)
- **Keep** bf16 vision tower upcast for <8-bit JANG profiles
- **Keep** deep-copy parameter approach (mx.eval + mx.array copy) for stream handling
- **Keep** VLMModelAdapter wrapping
- **Keep** Nemotron-H weight fix, bf16 auto-switch for large expert models
- Import from `.base import BaseEngine, GenerationOutput` (same path)
- Import `AsyncEngineCore` from `.engine_core` (verify path in v0.4.x)

### 2. `omlx/model_discovery.py` — JANG model detection
Add `jang_config.json` detection (~60 lines from PR #364 / marzukia):
- Check for `jang_config.json` in model directory
- Return `engine_type="jang"` when detected
- Order: check before embedding/reranker detection

### 3. `omlx/engine_pool.py` — JANG engine routing
Add `engine_type == "jang"` branch (~10 lines from PR #364):
- Create `JANGLoader(engine_type=EngineType.LLM)` 
- Handle model settings passthrough
- Memory tracking integration

### 4. `omlx/engine/__init__.py` — Register JANG engine

### 5. `pyproject.toml` — Add jang-tools dependency
Add `jang[mlx]>=0.1.0` or similar

### 6. `omlx/exceptions.py` — JANG error classes (if not present)

- vision config patching (native gemma4_vision support)
- Executor-based loading experiments (event-loop loading is the correct approach)

## Blocking Risk

The Metal stream issue (`There is no Stream(gpu, 1) in current thread`) could still occur with mlx-vlm 0.6.3 + jang_tools on Gemma 4 VLM models. The deep-copy parameter approach is the mitigation. If it persists, the fix needs to go upstream to jang_tools.
